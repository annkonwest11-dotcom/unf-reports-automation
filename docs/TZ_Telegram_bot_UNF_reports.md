# Техническое задание: автоматические отчёты из 1С:УНФ в Telegram и Google Sheets

> Документ предназначен для ИИ-ассистента-разработчика (терминальный coding-агент). Формулировки даны как требования к реализации. Где есть выбор — указано рекомендованное решение и допущения. Незакрытые вопросы вынесены в раздел «Открытые вопросы»: их нужно уточнить у заказчика до старта кодинга.

---

## 1. Контекст и ограничения среды

- Две **отдельные** информационные базы **1С:Управление нашей фирмой 3.0** (далее УНФ):
  - **База А** — «ИП Перфильев» (УНФ 3.0).
  - **База Б** — «ИП Губарев» (УНФ 3.0).
- Обе базы работают в **облаке 1С (сервис 1cfresh, «1С:Предприятие через интернет»)**. Это даёт жёсткие ограничения:
  - Нет доступа к серверу 1С и к веб-серверу → **публикация HTTP-сервисов и webhook на стороне 1С недоступна**.
  - Доступны **только исходящие HTTPS-запросы** из встроенного языка 1С (`HTTPСоединение`/`HTTPЗапрос`).
  - Доработка ведётся **только через расширение** конфигурации (типовую менять нельзя). Загрузка расширения требует прав администратора базы.
  - **Регламентные задания в облаке выполняются не чаще одного раза в минуту** и последовательно. Мгновенный отклик не гарантируется; допустимая задержка — до ~1–2 минут.
  - **Базы изолированы**: база А не видит данные базы Б и наоборот. Любое объединение данных делается во внешнем слое.

**Вывод по архитектуре:** объединять данные двух баз и формировать итоговый отчёт внутри 1С нельзя. Сборка, объединение, генерация Excel-дашборда, отправка в Telegram и запись в Google Sheets выполняются во **внешнем слое — Google Apps Script (GAS) Web App**. 1С только выгружает свои данные исходящими запросами и забирает «команды по запросу» из очереди.

## 2. Целевая архитектура

Компоненты:

1. **Расширение 1С в базе А и в базе Б (одинаковое, с параметром идентификатора базы).**
   - Регламентное задание «Сбор и выгрузка показателей».
   - Формирует JSON с показателями (см. раздел 4) за нужный период.
   - Делает `POST` на endpoint GAS (`/ingest`) с указанием `base_id` (`perfilev` / `gubarev`) и `period`.
   - Отдельное регламентное задание «Опрос очереди запросов» (раз в минуту): забирает из GAS (`/pull-commands`) запросы «по диапазону»/«на текущий день», исполняет, отправляет результат на `/ingest`.

2. **Google Apps Script Web App (внешний слой, единая точка интеграции).**
   - Endpoint `/ingest` — принимает данные от обеих баз, складывает в Google Sheets, помечает, что база отчиталась.
   - Когда пришли данные от **обеих** баз за один период — собирает **итог (А + Б)**, заполняет конкретные ячейки шаблона-дашборда (см. раздел 5), генерирует **Excel** и отправляет файл в Telegram.
   - Endpoint Telegram **webhook** — принимает команды от пользователя в боте (`/today`, `/range ...` и т.п.), кладёт их в очередь команд.
   - Endpoint `/pull-commands` — отдаёт 1С невыполненные команды из очереди.
   - **Триггеры по времени GAS** для еженедельного/ежемесячного/полугодового/годового отчёта (инициируют сбор, дёргая 1С через очередь, либо ожидают планового POST от 1С — см. раздел 6).

3. **Google Sheets** — рабочая книга:
   - Лист `RAW_perfilev`, `RAW_gubarev` — приёмники сырых данных по базам.
   - Лист `DASHBOARD` — шаблон с конкретными ячейками (заполняется значениями; см. раздел 5).
   - Лист `LOG` — служебный журнал запусков и ошибок.
   - Лист `QUEUE` — очередь команд «по запросу».

4. **Telegram Bot** — уже создан у заказчика (токен есть). Используется для приёма команд и доставки Excel-файлов.

Схема потока (ежедневный отчёт):
```
09:30  1С(База А) ──POST /ingest(perfilev, today)──┐
09:30  1С(База Б) ──POST /ingest(gubarev, today)──┤
                                                   ▼
                              GAS: записать RAW, проверить «обе пришли»
                                                   ▼
                  собрать ИТОГ(А+Б) → заполнить ячейки DASHBOARD
                                                   ▼
                 экспортировать Excel → sendDocument в Telegram
```

Поток «по запросу» (произвольный диапазон):
```
Пользователь → бот: /range 01.05.2026 31.05.2026
GAS webhook → положить команду в QUEUE
1С(А) и 1С(Б) (раз в минуту) → /pull-commands → видят команду → собирают данные за диапазон → POST /ingest
GAS → собрать ИТОГ → Excel → отправить в тот же чат
```

## 3. Состав баз и объединение

- Отчёт формируется **по каждой базе отдельно** и **итогом (А + Б суммарно)**.
- В Excel-файле и в дашборде должно быть видно три среза: **Перфильев**, **Губарев**, **Итого**.
- Объединение — **только в GAS**, после получения данных от обеих баз за один и тот же период и диапазон дат.
- Если одна из баз не прислала данные в течение N минут (по умолчанию 15) — отправить отчёт по доступной базе с пометкой «данные второй базы не получены» и записать ошибку в `LOG`.

---

## 4. Состав отчёта (показатели)

Все блоки считаются **за выбранный период** и, где указано, **в сравнении с предыдущим аналогичным периодом** (для динамики/роста/падения). Реализовать на данных УНФ 3.0; конкретные регистры/документы сопоставить по метаданным УНФ (ориентиры даны как подсказки, проверить в конкретной конфигурации).

### 4.1. Взаиморасчёты (кратко)
- Сальдо взаиморасчётов с контрагентами на конец периода: сколько нам должны / сколько должны мы (свёрнуто).
- Краткий формат: 2–4 ключевые цифры, без детализации по каждому контрагенту.
- Ориентир по данным: регистры взаиморасчётов с покупателями/поставщиками УНФ.

### 4.2. Продажи
- **Сумма продаж** за период (выручка).
- **Динамика продаж**: изменение к предыдущему аналогичному периоду, в ₽ и в %.
- **Средний показатель**: средние продажи в день (или средний чек/средний заказ — уточнить, см. открытые вопросы), за период.
- **Потенциальный оборот (прогноз)**: экстраполяция ожидаемого оборота на основе текущей динамики (например, run-rate: фактический темп × оставшийся горизонт периода). Метод прогноза описать в коде и в комментарии; по умолчанию — линейная экстраполяция по среднедневным продажам.
- Ориентир по данным: документы отгрузки/реализации, регистр продаж/выручки УНФ.

### 4.3. Активность клиентов
- Анализ активности клиентов за период в сравнении с предыдущим:
  - клиенты с **проседанием по заказам** (снижение количества/суммы заказов);
  - клиенты с **ростом**;
  - клиенты с **падением** (вплоть до прекращения заказов).
- Вывести топ-N по каждой категории (по умолчанию N = 5) с цифрами изменения.
- Ориентир по данным: документы «Заказ покупателя», продажи в разрезе контрагентов.

### 4.4. Дебиторская задолженность
- **Общая** дебиторка на конец периода.
- **Просроченная** дебиторка (по срокам оплаты / договорным условиям).
- **Топ-должников** (по умолчанию топ-5) отдельно по общей и по просроченной, с суммами и днями просрочки.
- Ориентир по данным: регистры расчётов с покупателями, сроки оплаты по заказам/счетам.

## 5. Запись в Google Sheets (конкретные ячейки)

Способ записи — **заполнение конкретных ячеек шаблона** (НЕ дописывание строк-журнала).

- Лист `DASHBOARD` оформляется заранее как шаблон с подписями и сеткой; ассистент создаёт его программно или принимает готовый.
- Значения пишутся в **именованные/жёстко заданные адреса ячеек**. Привести **карту ячеек** (cell map) в коде в виде конфигурации, например:

| Показатель | Перфильев | Губарев | Итого |
|---|---|---|---|
| Продажи, период | `C5` | `D5` | `E5` |
| Продажи, динамика % | `C6` | `D6` | `E6` |
| Средние продажи/день | `C7` | `D7` | `E7` |
| Прогноз оборота | `C8` | `D8` | `E8` |
| Взаиморасчёты: нам должны | `C11` | `D11` | `E11` |
| Взаиморасчёты: мы должны | `C12` | `D12` | `E12` |
| Дебиторка общая | `C15` | `D15` | `E15` |
| Дебиторка просроченная | `C16` | `D16` | `E16` |
| Дата/период отчёта | `B2` | — | — |

> Адреса выше — **пример**, ассистент согласует финальную карту ячеек с заказчиком (см. открытые вопросы) или сгенерирует шаблон сам и зафиксирует карту в конфиге.

- Топы (клиенты, должники) — в отдельные диапазоны/листы, т.к. это списки переменной длины: завести блоки фиксированного размера (топ-5) с заданными ячейками.
- Каждая запись перезаписывает ячейки актуальными значениями за выбранный период; история (если нужна) — опционально дублируется в лист-журнал (по умолчанию выключено).

## 6. Расписание и запуск

Отчёты и триггеры:

| Отчёт | Период данных | Когда | Кто инициирует |
|---|---|---|---|
| Ежедневный | текущий день | каждый день в **09:30** | регл. задание 1С в обеих базах |
| Еженедельный | прошедшая неделя | начало недели (день/время — уточнить) | триггер GAS / регл. задание 1С |
| Ежемесячный | прошедший месяц | начало месяца | триггер GAS / регл. задание 1С |
| Полугодовой | прошедшие 6 мес. | начало полугодия | триггер GAS / регл. задание 1С |
| Годовой | прошедший год | начало года | триггер GAS / регл. задание 1С |
| По запросу — текущий день | текущий день | по команде в боте | пользователь → очередь → 1С |
| По запросу — диапазон | произвольный диапазон дат | по команде в боте | пользователь → очередь → 1С |

- Часовой пояс зафиксировать явно (по умолчанию — МСК, Europe/Moscow). Согласовать с заказчиком.
- Ежедневный запуск надёжнее планировать **в самой 1С** (регламентное задание на 09:30), т.к. инициатором выгрузки должна быть 1С (только она имеет доступ к данным).
- Команды «по запросу» исполняются через очередь: бот не может «дёрнуть» облачную 1С напрямую, поэтому 1С раз в минуту опрашивает очередь команд в GAS.

### Команды бота (минимум)
- `/today` — отчёт за текущий день немедленно (через очередь).
- `/range ДД.ММ.ГГГГ ДД.ММ.ГГГГ` — отчёт за произвольный диапазон.
- `/help` — список команд.
- (Опционально) `/week`, `/month` — быстрые пресеты.

## 7. Форматы данных (контракт 1С ↔ GAS)

### 7.1. POST `/ingest` (из 1С в GAS)
```json
{
  "auth_token": "СЕКРЕТ_ОБЩИЙ_С_GAS",
  "base_id": "perfilev",
  "report_type": "daily",            // daily|weekly|monthly|halfyear|yearly|ondemand
  "period_start": "2026-06-18",
  "period_end": "2026-06-18",
  "generated_at": "2026-06-18T09:30:12+03:00",
  "request_id": "uuid-если-по-запросу-иначе-null",
  "metrics": {
    "settlements": { "they_owe_us": 0, "we_owe": 0 },
    "sales": {
      "total": 0,
      "prev_total": 0,
      "dynamics_abs": 0,
      "dynamics_pct": 0,
      "avg_per_day": 0,
      "forecast_turnover": 0
    },
    "clients_activity": {
      "growing":   [ { "name": "", "delta_abs": 0, "delta_pct": 0 } ],
      "declining": [ { "name": "", "delta_abs": 0, "delta_pct": 0 } ],
      "falling":   [ { "name": "", "delta_abs": 0, "delta_pct": 0 } ]
    },
    "receivables": {
      "total": 0,
      "overdue": 0,
      "top_total":   [ { "name": "", "amount": 0 } ],
      "top_overdue": [ { "name": "", "amount": 0, "days_overdue": 0 } ]
    }
  }
}
```

### 7.2. GET/POST `/pull-commands` (1С опрашивает очередь)
- Запрос: `{ "auth_token": "...", "base_id": "perfilev" }`
- Ответ:
```json
{
  "commands": [
    {
      "request_id": "uuid",
      "chat_id": 123456789,
      "report_type": "ondemand",
      "period_start": "2026-05-01",
      "period_end": "2026-05-31"
    }
  ]
}
```
- После исполнения 1С шлёт результат на `/ingest` с тем же `request_id`; GAS помечает команду выполненной.

### 7.3. Telegram
- Доставка файла: метод **`sendDocument`** на `https://api.telegram.org/bot<TOKEN>/sendDocument`, файл — сгенерированный **Excel (.xlsx)**.
- Webhook бота установить на URL Web App GAS (`setWebhook`).

## 8. Excel-файл для Telegram

- Формат: **.xlsx**, «с понятным оформлением и дашбордом».
- Содержимое:
  - Титульный блок: период, дата формирования, какие базы вошли.
  - Сводный дашборд: три среза (Перфильев / Губарев / Итого) по блокам разделов 4.1–4.4.
  - Графики/диаграммы: динамика продаж, структура дебиторки (общая vs просроченная), топ-должники, топ растущих/проседающих клиентов.
  - Отдельные листы с детализацией по каждой базе.
- Генерация Excel — в GAS. Возможные пути (ассистент выбирает и обосновывает):
  - заполнить заранее свёрстанный Google Sheets-шаблон с готовыми графиками и **экспортировать диапазон/книгу как .xlsx** (через export-URL/Drive API) — предпочтительно, т.к. оформление и графики делаются один раз в шаблоне;
  - либо сгенерировать .xlsx сторонней библиотекой.
- Оформление: единый стиль, читаемые заголовки, денежный формат ₽, цветовое выделение роста/падения (зелёный/красный), выделение просрочки.

## 9. Безопасность

- Хранить секреты вне кода: токен Telegram, общий `auth_token` 1С↔GAS, ID Google-таблицы — в Script Properties (GAS) и в константах/защищённом хранилище расширения 1С.
- `/ingest` и `/pull-commands` проверяют `auth_token`; запросы без валидного токена отклоняются.
- Telegram-команды принимать только из разрешённого списка `chat_id` (whitelist).
- В логах не печатать токены.

---

## 10. Обработка ошибок и журналирование

- Все запуски и ошибки — в лист `LOG` (время, база, тип отчёта, статус, сообщение).
- Если база не ответила за N минут — частичный отчёт + пометка.
- Ретраи исходящих запросов из 1С: до 3 попыток с паузой.
- Уведомление администратору в Telegram при критической ошибке (опционально).

## 11. Этапы реализации (для ассистента)

1. Поднять GAS Web App: endpoints `/ingest`, `/pull-commands`, Telegram webhook; структура Google Sheets (`RAW_*`, `DASHBOARD`, `LOG`, `QUEUE`); карта ячеек.
2. Реализовать в GAS: приём данных, объединение А+Б, заполнение ячеек, генерацию Excel, `sendDocument`, обработку команд бота, тайм-триггеры периодических отчётов.
3. Расширение 1С (общее для двух баз): процедуры расчёта показателей 4.1–4.4 за период и за диапазон; сериализация JSON по контракту 7.1; исходящий POST `/ingest`.
4. Регл. задание «ежедневно 09:30» + регл. задание «опрос очереди раз в минуту» (`/pull-commands` → расчёт → `/ingest`).
5. Тестовый прогон: ежедневный отчёт, отчёт по запросу с диапазоном, проверка объединения и оформления Excel.
6. Развёртывание: загрузка расширения в обе облачные базы (нужны права администратора), установка webhook, настройка whitelist чатов.

## 12. Открытые вопросы (уточнить у заказчика до старта)

1. **«Средний показатель» в продажах** — это средние продажи в день, средний чек или средний заказ? (По умолчанию принят «средние продажи в день».)
2. **Метод прогноза «потенциального оборота»** — устроит ли линейная экстраполяция по среднедневным продажам, или нужен иной (с учётом сезонности, план/факт)?
3. **Точное время недельного/месячного/полугодового/годового отчётов** (день и час) и **часовой пояс** (по умолчанию Europe/Moscow, 09:30).
4. **Получатели**: список `chat_id`/каналов, куда слать; один чат на оба ИП или разные.
5. **Карта ячеек дашборда**: есть готовый шаблон Google Sheets, или ассистент верстает его сам?
6. **Глубина топов** (по умолчанию топ-5) и критерий «просрочки» (по сроку оплаты заказа/счёта).
7. **Состав «взаиморасчётов кратко»** — только сальдо, или ещё разбивка покупатели/поставщики.
8. **Права администратора** в обеих облачных базах для загрузки расширения — подтвердить наличие.
9. Подтвердить, что **OData/REST-доступ к облачным базам недоступен** (тогда выгрузка строго инициируется изнутри 1С — как заложено в этом ТЗ).
